# Water-Rights Administering Agencies — Colorado River Basin States
## A verified inventory for Basin's data pipeline

Compiled 2026-08-05/06. Every claim below is tagged with its verification method:
- **[curl]** — verified directly by the orchestrating agent via `curl -s -L -A "Mozilla/5.0 ..."`, exact command/URL and observed response cited.
- **[curl, independently re-verified]** — a sub-agent's WebFetch finding that the orchestrator then re-confirmed with its own curl call (highest confidence after curl-original).
- **[WebFetch, unverified by curl]** — found only by a sub-agent using WebFetch (LLM-summarized fetch, not raw curl) because that sub-agent's environment lacked the Bash tool. Flagged wherever this is the only evidence. Treat as lower confidence than [curl].
- **UNVERIFIED** — could not be confirmed either way within the time available; explicitly not filled in from memory.

**Grading scale** (per task spec): A = REST API or bulk download verified working via curl (real structured data returned); B = web search/report tool that returns structured, scrapable results (HTML table, no auth); C = search interface exists but is bot-blocked, JS-rendered/Salesforce-Aura shell, or ASP.NET-postback-only (real tool, not simply GET-scrapable); D = offline/email/PDF/notarized-form only.

**Important methodological note:** Three sub-agents were dispatched in parallel to probe WY/UT, NM/AZ, and NV/CA. The `research-analyst` agent type does not have Bash tool access in this environment (confirmed by direct tool-invocation error). The NM/AZ agent therefore returned zero findings and correctly refused to fabricate data — the orchestrator did all NM/AZ probing directly via curl instead. The WY/UT and NV/CA agents substituted WebFetch (which does report raw HTTP status codes but LLM-summarizes body content) and explicitly self-flagged this deviation. The orchestrator subsequently re-verified the single most decision-critical claim from each of those two reports directly via curl (Utah's Change Application Tracker + ROC tracker; California's Standard Change Petition table + CalWATRS/eWRIMS status; Nevada's PermitSearch/Hydrographic forms + DCAT feed) and all re-checks corroborated the WebFetch findings. Claims from those two agents that were **not** independently re-checked are marked [WebFetch, unverified by curl] below.

## 0. COLORADO — Division of Water Resources (DWR) / CDSS — baseline, already integrated

**Official name:** Colorado Division of Water Resources, part of the Colorado Department of Natural Resources. Statutory role: administers the prior-appropriation permit system and water-court-adjudicated rights (adjudication itself happens in Colorado's seven water courts, not at DWR — DWR administers/enforces post-adjudication).

**Record systems (all [curl]):**
- CDSS REST API root: `https://dwr.state.co.us/Rest/GET/api/v2` — help page `https://dwr.state.co.us/rest/get/help` returned HTTP 200, title "CDSS REST Services" (164KB Swagger-style docs).
- `GET /waterrights/transaction/?format=json&pageSize=1` → HTTP 200, real JSON (single water-right transaction record with full metadata: WDID, adjudication date, location, structure type).
- `GET /waterrights/transaction/?format=json&wdid=7200645&pageSize=5` → HTTP 200, confirms **filterable by WDID** — i.e., queryable per-structure, not just paginated dump.
- `GET /structures/divrec/divrecday/?wdid=7200645&format=json` → HTTP 200, **13.2MB** of real daily diversion records (1968–present for this structure).
- `Tools/WaterRights/Transactions/324379` (individual change-case detail page, the human-facing equivalent of a "transaction") → HTTP 200, 101KB real HTML.

**Grade: A** (REST API, confirmed filterable, confirmed bulk-sized responses). **Change-of-use queryable: Yes** — the `transaction` endpoint is literally Colorado's change-case/transfer log, filterable and already the backbone of Basin's `transactions_gv.json`. **Ownership:** not recorded by DWR (transactions show structure/applicant name at time of filing, not current beneficial owner) — falls through to county clerk/recorder, consistent with Basin's existing understanding. **No time-sensitive migration risk observed.**

## Top 3 findings that would change Basin's roadmap

1. **Arizona is not a dead end — it just isn't on azwater.gov.** The main ADWR website is fully Cloudflare-gated (403 on every path including `robots.txt`), which would make a naive pipeline conclude Arizona is unreachable (Grade D). But ADWR's actual system-of-record — Wells55, and critically a 99,775-record surface water rights filing database (`Filing_POD`) with owner name, mailing address, priority date, and a conveyance-number field — sits wide open on `services.arcgis.com` under a completely different domain, no authentication required. This flips Arizona from an assumed-worst state to a Grade-A bulk-data state, and should be prioritized ahead of states that only reach Grade B/C.

2. **The strongest change-of-use ("market signal") data isn't a REST API anywhere — it's plain HTML tables, in Utah and California specifically.** Utah's Change Application Tracker, Exchange Application Tracker, and ROC ownership-transfer tracker, and California's Standard Change Petition Notices table, are all live, current (dated into 2026), unauthenticated HTML tables naming the water-right holder and the transaction type — directly scrapable with a basic HTML-table parser, no login, no bot-blocking encountered. This should be the near-term build target for the transfer/change-of-use feature, ahead of any state's formal API. Wyoming and Nevada, by contrast, have no equivalent live tracker at all (PDF/notarized-form only) — pipeline effort there should be deprioritized or treated as a manual/periodic-check state.

3. **State agencies recording beneficial-ownership names directly is the norm, not the exception, among the states with modern systems** — this contradicts the working assumption in the task brief. New Mexico's bulk Points-of-Diversion CSV includes owner first/last name and full mailing address; Arizona's Filing_POD and Well Registry both include owner name and address; California exposes the water-right-holder name in every petition and search record; Utah's ROC tracker names the submitting law firm/title company. The one clear exception is Wyoming, which has no live-searchable ownership data at all. In every case this is the *filer/permittee of record*, not necessarily a title-verified current beneficial owner — real-property deed ownership still requires a county recorder fallback — but for Basin's purposes (tracking who holds/administers a water right, not verifying legal title), this is substantially richer than the "no state records ownership" assumption implied, and changes how much county-level plumbing Basin actually needs to build.

## Secondary notes worth flagging

- **California's eWRIMS/CalWATRS migration is genuinely mid-flight and inconsistent**, not a clean binary. One legacy search path 500s, a different legacy search path still 200s with a real form, and the new CalWATRS portal is JS-only (Salesforce Aura) and unreachable via plain HTTP. Anyone building a CA integration should target the ArcGIS FeatureServer and the Standard Change Petition table (both stable, both outside the migration) rather than either version of eWRIMS or the CalWATRS portal itself.
- **New Mexico's NMWRRS change-of-use/active-application tracker equivalent (if one exists) was not confirmed** — this is the single biggest open item from this pass and should be the first follow-up (test the "Active Case List" nav link and the NMWRRS report endpoints with POST requests).
- **Nevada's and Wyoming's richest-sounding tools (ASP.NET permit/hydrographic search, e-Permit) are real but not simply GET-scrapable** — both need a follow-up pass specifically testing whether ASPX postback state can be simulated with curl (fetch `__VIEWSTATE`/`__EVENTVALIDATION` from the GET response, then POST them back with query params), which was out of scope for this initial survey.
- **Utah's ArcGIS backend returns HTTP 500 on every direct REST-services-listing guess**, despite the human-facing map tool working — this deserves one more look (likely needs a `Referer` header matching the map.asp page, or the service folder name is simply not one of the seven guessed).
